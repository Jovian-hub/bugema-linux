# Contributing to Bugema Linux

Thank you for your interest in contributing to **Bugema Linux**, an open-source project of the **Bugema Open Source Community (BOSC)** at Bugema University, Uganda.

Bugema Linux is developed as both an institutional open-source technology project and a practical learning and research platform. Contributions from students, staff, researchers, developers, alumni, and the wider open-source community are welcome.

## 1. Before You Contribute

Before starting work, please:

1. Read this document.
2. Check the existing GitHub issues.
3. Avoid duplicating an existing issue or feature.
4. Create or identify an issue describing the work.
5. Discuss major architectural or security changes before implementation.
6. Follow the project's coding, documentation, testing, and security practices.

## 2. Contribution Areas

Contributors may participate in areas including:

* Linux system configuration
* Desktop customization
* Bugema branding
* Software packaging
* Development tools
* Educational applications
* Networking
* Cybersecurity
* Artificial intelligence
* Internet of Things
* System administration
* Installer development
* Testing and quality assurance
* Build automation
* DevOps and CI/CD
* Documentation
* User experience
* Research and experimentation

## 3. GitHub Workflow

Bugema Linux follows an issue-driven development workflow.

```text
Issue
  ↓
Assignment
  ↓
Feature Branch
  ↓
Development
  ↓
Testing
  ↓
Pull Request
  ↓
Review
  ↓
Approval
  ↓
Merge
```

Contributors should normally avoid committing directly to the `main` branch.

## 4. Issues

Before beginning significant work, create or identify a GitHub issue.

A good issue should clearly explain:

* What needs to be done
* Why it is needed
* Expected outcome
* Relevant technical information
* Testing requirements
* Documentation requirements

For student assignments, the issue may be created by the course instructor or project team.

## 5. Branches

Create a separate branch for your work.

Recommended naming conventions:

```text
feature/desktop-theme
feature/installer
feature/software-packages
feature/network-tools
feature/build-system

fix/boot-error
fix/package-conflict

docs/installation-guide
docs/user-guide

test/virtualbox-installation
test/hardware-compatibility
```

Keep branch names short and descriptive.

## 6. Commits

Use clear and meaningful commit messages.

Recommended prefixes include:

```text
feat:     new functionality
fix:      bug correction
docs:     documentation
test:     testing
build:    build system
ci:       continuous integration
security: security-related change
refactor: code restructuring
chore:    maintenance
```

Examples:

```text
feat: add Bugema desktop branding
fix: resolve network configuration issue
docs: add installation instructions
test: validate ISO in VirtualBox
build: configure ISO build environment
ci: add automated build workflow
security: update package verification process
```

Avoid vague messages such as:

```text
update
changes
my work
final
new stuff
```

## 7. Pull Requests

All significant changes should be submitted through a Pull Request.

A Pull Request should:

* Reference the relevant issue.
* Clearly describe the changes.
* Explain how the changes were tested.
* Include documentation where necessary.
* Identify known limitations.
* Avoid unrelated changes.

Example:

```text
Closes #25
```

## 8. Code Review

Pull Requests may be reviewed by:

* Project maintainers
* Relevant technical team leads
* Assigned student reviewers
* Subject-matter experts

Reviewers may request:

* Code changes
* Additional tests
* Documentation
* Security improvements
* Architectural clarification

Contributors should respond constructively to review comments.

## 9. Testing

Changes should be tested before submitting a Pull Request.

Depending on the contribution, testing may include:

* Virtual machine testing
* Hardware testing
* Installation testing
* Boot testing
* Network testing
* Application testing
* Security testing
* Regression testing
* Build testing

Testing results should be documented in the Pull Request.

## 10. Documentation

Technical changes should include appropriate documentation.

Examples include:

* Installation instructions
* Configuration instructions
* User guides
* Administration procedures
* Troubleshooting information
* Architecture documentation
* Development documentation

Documentation is considered part of the implementation rather than an optional addition.

## 11. Security

Security issues should not be publicly disclosed through ordinary GitHub issues when they could expose a vulnerability.

Security-related reports should follow the project's security reporting procedure.

Contributors should never intentionally introduce:

* Malware
* Backdoors
* Credential theft
* Unauthorized access mechanisms
* Destructive code
* Deliberately vulnerable configurations

## 12. Student Contributions

Students participating through the Open Source Systems course are encouraged to make genuine contributions to the Bugema Linux project.

Student work should:

* Be associated with a GitHub issue.
* Use a feature or task branch.
* Include appropriate commits.
* Be tested.
* Be submitted through a Pull Request.
* Receive peer review.
* Follow project standards.

Student contributions may become part of the main Bugema Linux project after technical review and approval.

Academic assessment and production acceptance are separate processes.

A contribution may receive academic credit while still requiring additional technical work before being merged into the production project.

## 13. Intellectual Property

Contributors are responsible for ensuring that the code, documentation, artwork, configurations, and other materials they submit can legally be contributed to the project.

Do not submit:

* Proprietary software
* Copyrighted materials without permission
* Confidential institutional information
* Personal information
* Credentials or secrets
* Unlicensed third-party assets

## 14. Third-Party Software

Bugema Linux may incorporate software from upstream open-source projects.

Contributors must respect the licenses and conditions applicable to third-party software.

Where appropriate, dependencies and licenses should be documented.

## 15. Communication

Technical discussions should preferably take place through the project's GitHub issues, discussions, and Pull Requests so that decisions remain accessible to future contributors.

Major architectural decisions should be documented rather than relying only on private conversations.

## 16. Quality Standards

Contributors should aim to produce work that is:

* Correct
* Secure
* Reproducible
* Maintainable
* Well documented
* Tested
* Understandable
* Compatible with the project architecture

## 17. Recognition

Meaningful contributions may be recognized through:

* GitHub contribution history
* Release notes
* Project documentation
* Contributor acknowledgements
* Student project records
* Research and publication opportunities where appropriate
  

## 18. Questions

If you are unsure about how to contribute, open a GitHub issue or discussion describing the problem and the proposed work.
